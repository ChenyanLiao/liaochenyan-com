MolloM · 2026.10.24

MolloM user manual

Prepare a desktop project, review results and follow runs on your phone. Find the right workflow in the MolloM manual.

For a first run, use one ligand. Load the public example, save the project and locate the receptor, reference ligand and box in the pocket view. Run a one-ligand Vina pilot. Open its score and pose before switching to your own library. Already have a trajectory? Start with trajectory analysis.

The desktop steps were checked against development version 0.301.0. The figures show an earlier build. Check your version in Settings and compare it with the downloads. To use your own AI client, follow the connection steps and give it the Agent guide (Markdown).

1. Getting started

1.1 Choose a first task

Use a familiar receptor and a few ligands. Work through import, preparation, the search box, a small trial and result review before running a large library.

If you already have a GROMACS system, start at chapter 10. If you have a wavefunction file, start at chapter 12. Start at chapter 13 for mobile monitoring and plans. Docking and MD have separate entry points; neither is a prerequisite for the other.

1.2 Choose where to work and where to compute

Use the desktop app to prepare structures, configure programs, schedule calculations and inspect results. Choose a local computer or an SSH server as the execution host. Enter program paths, input paths and resources for that host: remote paths are read on the server, local paths on your computer.

After connecting the phone to the monitoring service, you can inspect runs, results and logs from the paired device, and edit pending plans while permission remains valid. Before leaving the desktop, check that the computing host will stay awake and the monitoring service will keep running.

1.3 Find projects and settings

Under Projects and Templates, create a project, open a project JSON file or load the public example. Select your interface language in Settings.

Before running the example, check the input files, compute environment and search area. Run a small test first. Treat template values as starting points and adjust them for your structures and research question.

Read your first run through an AI client

  1. Use a client that supports MCP over stdio on the computer running MolloM. Node.js 18 or later must be available to the client. Calculations can still run on an SSH server.
  2. Under Settings → AI Agent · MCP, select read-only and apply the permission. Once the service shows as running, copy the connection JSON.
  3. Add the entry to your client’s MCP configuration alongside its existing servers. Use the generated paths. Keep the contents of the connection file out of chat. Leave MolloM open and reconnect the client.
  4. Give it the Agent guide and ask: “List up to five registered docking runs. Let me pick one before you read its status. Read only.” An empty list can be a successful connection to a workspace with no runs. Switch to task control, apply and reconnect only when you need a write operation.

2. Set up the compute environment

2.1 Run locally

  1. Open Compute Environment and Software Center and select local execution.
  2. Detect the environment again and inspect the programs it found.
  3. If a docking engine is already installed, select the actual executable, such as the Vina binary.
  4. Check that the working directory is writable and has enough free space.

After checking paths, run a small real job. This is where missing libraries, model files or device drivers are most likely to show up.

2.2 Connect over SSH

  1. Add a server using its hostname or an SSH Config alias.
  2. Enter the account and port and choose system authentication or a key file. Never paste a private key into a regular text field.
  3. Enter the server’s work directory and remote executable paths. If a Python path is needed, use the one on the server.
  4. Save the server, then test the connection and detect the environment.

Verify the host fingerprint on the first connection. For an unknown host or authentication error, check the connection in your system SSH client before retrying in MolloM. If an existing executable fails to start, read the probe output and check permissions, dependencies and environment.

On a cluster, choose a scheduler offered for this task. Enter the partition or queue, account, time limit and resources required by the site.

Locate the last successful step. An unknown host fingerprint calls for a check with the administrator. An authentication failure calls for checking the user and key. If SSH succeeded but the runtime check failed, check Python on the remote host. On Slurm, PENDING / Priority means the job is queued. QOSMinGRES means the resource request falls below the partition minimum, which can apply even to a CPU analysis.

2.3 Install or register software

In Software Center, choose the local computer or target server and refresh its software list. To install a version, review the installation and verification plan first, including the destination, licence and dependencies.

For an existing installation, reverify it before choosing to use that version. Some entries provide upstream installation instructions or let you register a program you installed separately. Read a failed verification’s output before proceeding; a directory existing is not proof that the program works.

3. Create a project and import structures

3.1 Keep the project easy to find

Create a named project under Projects and Templates. Give it a name that identifies the subject and purpose. One project can hold many runs and screening rounds; a minor adjustment does not require copying all the files.

Save after changing important settings. Export JSON for project settings alone; use chapter 9’s portable package to move inputs and results as well.

3.2 Add receptors and ligands

  1. Under Receptors and Ligands, add a receptor from a PDB or PDBQT file.
  2. Choose ligand files or a folder, or browse files on the server.
  3. Select the actual input format: PDBQT, SDF/SD, MOL2, MOL or SMILES.
  4. Recheck inputs and inspect the record count, engine-ready inputs and parsing issues.

One SDF file can contain several molecular records, so file and record counts may differ. Review problematic records and decide whether to correct, exclude or prepare them again before expanding the run.

3.3 Preserve provenance

Keep original files and traceable molecule identifiers. Prepared working states should remain traceable to a common parent. Name receptors clearly when comparing structures or conformations in one project.

Do not overwrite the original files with manually edited engine inputs. The preparation step produces working copies that you can check separately.

4. Prepare receptors and ligands

4.1 Decide what stays in the receptor

In Structure Preparation, specify chains or leave the field blank to keep all chains. Decide whether to remove ordinary water and whether to retain HETATM cofactors or metals. Check structural and literature evidence before removing functional water, metal ions or cofactors from a pocket.

Review missing or nonstandard residues and protonation. The current workflow reports structures it does not support; missing loops and protonation at the target pH need separate treatment.

4.2 Prepare ligand working states

Choose whether to keep the largest parent, enumerate tautomeric working states and limit the number of states per source record. Undefined stereochemistry is isolated by default. Enable it only when you know how those specific inputs should be handled.

Generate 3D coordinates for inputs that do not have them, then check charge, stereochemistry and bonds before docking.

4.3 Check changes after preparation

Prepare and check the input, review completed and problematic records, then open the preparation directory to inspect the files. In the before/after comparison, check heavy atoms, formal charge, fragments and coordinates.

Correct failures by cause. Keep the source files and generate fresh working copies so you can trace changes.

5. Set the search region

5.1 Locate the pocket

In the 3D pocket view, select the receptor. Toggle protein, ligand and surface display; drag to rotate, scroll to zoom and reset the view if needed.

Use a reference ligand to locate the pocket if one is available. It must share the current receptor’s coordinate system. Align the structures first if the coordinates came from a different structure.

5.2 Check the search box

Enter center XYZ and size XYZ in angstroms (Å). Check that the box covers the intended area and fits the ligand without including excessive unrelated space.

Check each receptor’s box separately. Save the project, then verify in trial results that poses appear where expected.

6. Configure the docking engine and resources

6.1 Choose and verify the engine

Find the program by name or category, consult its documentation and select it for this round. Set its executable on the target host and check the path.

Prefer a configured built-in integration. For a custom native integration, test commands, input and output parsing on a small job first.

6.2 Set Vina parameters and independent seeds

Select Vina, then set exhaustiveness, the maximum output poses, energy range and scoring function. Higher exhaustiveness costs more compute; use a trial to decide rather than maximizing everything.

Enter a list of independent seeds, one search per seed. Input records, enabled receptors and seeds together determine the task count. Review the round name and count before submission to catch unwanted receptors or repeated seeds.

6.3 Use GNINA

Choose how the CNN should be used, such as rescoring or refinement, and select a model or leave the field empty for the engine default. Choose CPU-only execution if GPUs should not be used.

For GPU execution, verify the software, driver and allocated resources, then check the trial log for the actual execution mode. Energy, CNNscore and CNNaffinity represent different quantities and have their own ranking direction. Set screening conditions separately.

6.4 Allocate concurrency, CPUs and GPUs

CPUs per task control the resources of one job; concurrency controls how many jobs run at once. Their product should fit the allocated CPU resources, with room for the operating system and I/O.

Check queue, time, memory and GPU requests on a cluster. Trial throughput and memory use before scaling. More concurrency can slow a batch when storage, GPU memory or CPUs are contended.

7. Trial a small batch and submit a full run

7.1 Trial a small input set

In the trial and timing view, set a ligand sample size, start the real trial and open its tasks. This runs the chosen program and consumes resources on the selected host.

Review output poses, result parsing and logs. The estimate reflects this sample and configuration, not queueing, preparation, transfers or export. Run another trial after changing the engine, model, exhaustiveness or host.

Inspect a successful pose in the pocket and read the original log for one failed ligand. A single small ligand is a poor timing sample for a library containing many large molecules. Record sample size and concurrency; allow extra time for queuing, transfers and export.

7.2 Submit the batch

In Tasks and Progress, confirm the prepared inputs, receptors, seeds and resources, then submit a new docking run. Open its saved parameters to check the actual configuration.

Watch completed, failed and pending work. Open run events, raw logs or the run folder to diagnose a problem. Start a new run when changing settings for a new round so results from different conditions stay separate.

7.3 Pause, cancel or recover a run

Pausing stops the executor from claiming new tasks; tasks already running continue. Resume when ready. Cancelling remaining work preserves results already written.

Select only failed tasks that need retrying, retaining successful results and attempt history. After a network interruption or unknown status, reconnect and refresh the original run instead of submitting it again. An independent executor can continue after the desktop window closes. Host sleep, shutdown and scheduler termination need separate handling.

8. Screen results and create the next round

8.1 Find records worth inspecting

Choose a run in Results and Screening. Apply a name filter, primary cutoff or advanced multi-metric filters. Review poses, provenance and metrics rather than reading only the first score.

All conditions should apply to the same pose. Do not average unrelated scoring methods. Docking prioritizes structures to investigate; binding and activity require independent evidence.

8.2 Limit duplicates without losing diversity

Keep one representative per parent or limit representatives per RDKit scaffold when appropriate. Avoid merging early if differences between working states are the subject of the comparison.

Check the filtered count and select records to carry forward. For unusually high scores, clashes or implausible poses, review the input and preparation history first.

8.3 Create a new round

Open screening rounds, select a finished run, set conditions and count candidates. Name the next round and choose its engine. Keep the original prepared input or use the best eligible pose from this round.

Choose an output directory and create the new round. Inspect its inputs and configuration before trialling or submitting it. Creating the round does not start a calculation.

For practice, select Vina affinity and preview a cutoff of ≤ −7.0 kcal/mol. Check the count before creating a round. If you switch to GNINA, choose its score and direction afresh: higher CNNscore is preferred. Open the new round and check the receptor, ligand count and engine before submitting.

9. Export results and move projects

9.1 Export results for collaborators

In Structures and Results Export, choose filtered results or only checked records. Export the CSV, structures, receptor, configuration and report needed. Select all eligible poses to include multiple poses.

Check successes and failures in the report. SDF conversion can fail without reliable atom mapping; inspect the retained PDBQT and report. Do not count missing structures as delivered. Large exports support pause and checkpoint recovery.

After closing MolloM mid-export, reopen the original project, find the same export and check its destination before resuming. Inspect any conflicting file before changing it. Reconcile successes and failures with the requested formats. Multiple poses per ligand can give different row, ligand and file counts.

9.2 Build a portable project bundle

Preview the bundle. Include remote inputs and results from finished tasks if needed, then choose a directory and export.

On the other computer, select the bundle’s Project.htvs.json and review the preview before importing it as an independent project. Reconfigure software, authentication and paths for that host. Retain historical results for comparison; create new runs from the imported project.

9.3 Manage storage

Scan disk space and references in Projects and Storage. Check what files are for and what uses them before clearing caches. Only clear the safe cache entries shown in the preview.

Follow your backup plan for original inputs, final results and preparation records. Move projects as bundles when actual inputs must travel with settings.

10. Prepare a molecular dynamics system

10.1 Choose the starting point

Open Molecular Dynamics · GROMACS. Build from a standard protein PDB, or inspect and import existing coordinates, topology or a TPR.

For a docking result, generate the handoff SDF, confirm atom identities and coordinates, then proceed to ligand parameterization. Decide the force field, protonation, ligand charge and composition first.

10.2 Prepare the ligand and assemble the complex

In Ligand Parameters, choose configured ACPYPE / AmberTools with GAFF or GAFF2, and supply the integer net charge and charge method. Check input and environment, prepare an isolated task, submit it after review and inspect the topology handoff.

Complex assembly currently covers a dry AMBER protein and a single GAFF/GAFF2 ligand. Select protein GRO/TOP, ligand ITP and bound-pose GRO, then check the coordinate system, atom order and force-field compatibility. Check atom correspondence and inputs before building the isolated complex, then pass it to system setup for solvent, ions and validation.

10.3 Add solvent and ions

  1. Choose a standard protein PDB, a dry system with topology or an existing complete system.
  2. Set the execution host, system directory and inputs, then check structures and installed force fields.
  3. Choose an installed force field and compatible water model. Set the box shape, solute-to-edge distance, salt concentration, ions and neutralization.
  4. Review terminal and protonation settings, save the build plan and preview commands.
  5. Submit the build once checked. Inspect the outputs before moving to a multi-stage workflow or MD import.

System box distances use nm, not the Å used by the docking search box. Use an appropriate specialist method for membrane proteins, unusual residues or complex cofactors and import the prepared system. A built system still needs minimization and equilibration.

10.4 Import an existing system

Under Import or Connect System, choose an existing TPR or coordinates, topology and MDP. Set the directory and relative file paths on the target host. Add index, position-restraint reference coordinates and a checkpoint if needed.

Check GROMACS, then check the system and import it as a submittable job. Read input and preprocessing output before submitting; choose monitoring only if you are following an external run.

11. Set up and run multi-stage simulations

11.1 Create a workflow and independent replicates

Create a workflow and specify the number of independent replicates and starting seeds as needed. Review input, MDP and resources for every stage: EM, NVT, NPT and production.

Built-in short workflows check that the workflow runs; do not use them unchanged for your own equilibration or production. Review duration, temperature and pressure coupling, position restraints and constraints. Save the workflow without submitting.

11.2 Edit MDP and review preprocessing

In the GROMACS parameter workbench, search by native parameter name and check integrator, dt, nsteps, output frequencies, coupling and constraints. The time step and step count determine total duration.

Check for duplicate keys and retain useful comments when importing MDP files. Read preprocessing warnings verbatim and fix their cause rather than increasing maxwarn to skip unresolved problems.

11.3 Start a stage and allocate resources

Before starting the current or next stage, review the host, scheduler resources and mdrun settings. Match threads, PME, GPU settings and requested queue resources. Use a short run’s logs to guide the resource choices for a long run.

Check outputs and system state before starting another stage. Resolve a failed or stopped stage instead of skipping necessary steps.

11.4 Stop, resume and inspect logs

To stop cleanly, save a checkpoint and stop. Resume using the original run’s checkpoint and read the log to confirm where it continued. The step limit is the final step number, not how many steps to add.

Read and refresh logs. If constraints fail, energies are abnormal or structures look implausible, check the system and settings and return to preparation or equilibration if needed. Passing state between stages and resuming the same stage use distinct workflows.

12. Inspect trajectories and wavefunctions

12.1 Set up a trajectory analysis

Once the trajectory is no longer being written, add it as a read-only analysis source. Select TPR and XTC/TRR; add EDR and logs if needed. Check the trajectory, atom groups and energy terms.

Choose the time window, frame interval, PBC handling, reference, fitting group and measurement group. Start with RMSD, RMSF, radius of gyration, SASA, hydrogen bonds, contact distances or energy. Select PCA, clustering or density according to the research question and available tools.

Preview custom atom selections. Ligand RMSD after fitting the protein and ligand RMSD after fitting the ligand answer different questions; record which you used.

A trajectory saved every 10 ps from 0 to 20 ns has 2,001 frames including both endpoints. Sampling every 100 ps gives 201 curve points. Select a time and check the actual frame. If the scheduler says FAILED, compare the last simulation step, final frame time and wrapper error before resuming. The requested duration alone cannot tell you how far the run got.

12.2 Review, compare and export analyses

Read method and provenance before looking at plots or loading a trajectory preview. Inspect the actual frame behind an unusual point instead of judging from curve shape alone.

Load MD jobs and their analyses, then add two to eight records to comparison. Match the time window, alignment and selections before comparing curves and methods. Export comparison JSON if needed, and retain differences between independent replicates.

12.3 Check Multiwfn inputs

In Multiwfn Input Check, select a wavefunction file on the local or SSH host. The input check supports FCH/FCHK, single-frame MWFN and supported nonmagnetic GTO WFN/WFX.

Review atoms, electrons, basis, orbitals and density data, and resolve missing or incompatible entries first. Install or verify Multiwfn on the target host. A docking pose or MD frame can supply geometry for a separate quantum-chemistry calculation; generate the wavefunction there before importing it.

12.4 Set up an analysis and inspect 3D density

Enter the Multiwfn path, method, CPU threads and timeout and preview the task. Check electronic state, method and licence, then save without running. Submit separately when ready.

For density, set grid origin, spacing and point counts in Bohr. Check coverage and total point count, then load the result and set and update the isosurface threshold.

Choose a method enabled by the input check. Mulliken and Löwdin charges need suitable basis-set information; renaming a file cannot supply it.

12.5 Export and archive analyses

Export cube files, logs, method outputs and settings. Preview a task archive and select a destination. Large copies can be paused and resumed.

Import task archives for offline review. Give entries aliases, hide or remove them, or restore entries removed in error. List management is separate from original calculations; check before deleting files.

13. Connect your phone to a computer or server

Pair a device before monitoring progress, taking notes or editing pending plans from the phone.

13.1 Connect to the service and sign in

Start the monitoring service on the computer and confirm that the phone can reach it. Use the address provided by your own deployment or administrator, not the server’s SSH address.

  1. Open your account and devices from the profile tab or Settings.
  2. Enter the configured service address and connect.
  3. Enter your email and password and sign in.
  4. If account registration is available, create an account with a display name, email and password. Complete email verification if requested, then return to sign-in.

Check: The sign-in form closes and the current account and monitoring devices appear. If none are paired, continue to pairing.

Troubleshooting: Check the address and running service first. Sign in again after a session expires. If the app offers to resend a verification email, check your inbox and spam folder. Resending does not fix an unconfigured mail service. A local read-only connection is for the current device’s local service, not a remote computer.

13.2 Pair with a one-time code

  1. Generate a new pairing code in the computer’s monitoring agent. Check both devices use the same service address.
  2. In the phone’s account and devices view, enter the code and request pairing.
  3. On the computer, check the requesting account and confirm the pairing.
  4. Refresh devices on the phone.

Check: The computer appears under monitoring devices. Requesting pairing on the phone alone is not enough; the computer must confirm.

Troubleshooting: Generate a fresh code if the old one is invalid, used or expired. If confirmation is pending, verify the requesting account and the service address on each device.

13.3 Select a device to monitor

  1. Find the computer and check its name, last contact and status-report timestamps.
  2. Open that device and return to Progress.
  3. To switch devices, open the account view and select another computer.

Check: The selected device is marked and the home view shows runs for that connection. Computation can run on that computer or its connected server; check the local or remote execution label on the run.

Troubleshooting: Refresh the device list first. If disconnected, check sleep, the monitoring agent and the network. A disconnection does not mean the calculation failed; one run’s connection problem does not imply all devices are offline.

13.4 Review permissions and unpair

  1. Refresh devices and check the permissions and expiry on the relevant card.
  2. View runs with read access. To edit plans or submit calculations, grant the corresponding time-limited permission on the computer and refresh the phone. See chapter 18.
  3. Before unpairing, export research records you need to keep. Then select unpair and review the confirmation.

Check: Refreshed permissions match the desktop grant. After unpairing, the device stops supplying monitoring data to the account. Existing calculations remain on their original host.

Troubleshooting: Renew expired permission on the computer and refresh instead of retrying a disabled edit button. Before unpairing, signing out or switching connections, keep any needed local records; local copies are cleared as described by the app.

14. Find runs and read progress

14.1 Find a run from the Progress screen

  1. Open Progress.
  2. Use the overview counts for all, active or attention-needed runs to open the corresponding list.
  3. Pick a recent run and open details, or open the full run and project list.
  4. Compare the compute-side update time with the last successful read on the phone. They measure different events.

Check: Confirm the run, project, type and execution location. Last progress or unknown status reflects the most recent available read, not live progress.

Troubleshooting: If a run is missing, verify the device and search in Research. If reading stalls or the connection drops, reconnect and refresh tasks. Do not submit again.

14.2 Filter by project, type and state

  1. Open Research and search by name, project or identifier.
  2. Select a project and a compute type, such as Docking or MD.
  3. Filter by state, then refine by engine or local/remote execution if needed.
  4. Page through results or clear filters to start again.

Check: The scope is shown above the list. Directory search spans all its pages. An account connection searches synced records for the selected device, not just the displayed page.

Troubleshooting: Clear filters and check the selected project and type. If sync is partial, check earlier history on the computer. Offline searches cover saved local copies only.

14.3 Set refresh frequency and recover reads

  1. Set English in Settings to match this guide.
  2. Select refresh every 5, 10, 15 or 30 seconds, every 1, 2 or 5 minutes, or manually.
  3. Refresh tasks on the home screen to read immediately. If results or logs fail to load, retry in the detail view.

Check: The last successful read time updates. Manual mode stops scheduled reads. Changing the interval, closing the screen or locking the phone does not pause remote jobs.

Troubleshooting: If the timestamp is unchanged, look for connection messages. Refresh and confirm the device before retrying. Previously saved pages remain reference copies.

14.4 Filter notifications and open their runs

  1. After signing in and pairing, open Messages and refresh the list.
  2. Filter by read state or event type, such as failure, completion or connection changes. Page back for older messages.
  3. Mark individual messages read or unread. Open error logs, a run or a device from a message; the app selects the matching device and marks the message read after opening its destination.
  4. For a failure notification, check its time and attempt. If it refers to an older attempt, the displayed log is from the current attempt. Check the older log on the computer.

Check: The unread count and filtered list reflect message state. Read does not mean resolved. Use the opened run and its read time for current status.

Troubleshooting: Sign in when prompted; retry message refresh after checking the connection. Reset both filters if no messages match. Notifications for unpaired devices are historical and cannot open a destination. If access fails, verify the account and device and check the desktop record. Do not use the current log to explain an older attempt.

15. Inspect results and logs

15.1 Inspect Docking results

  1. Select a Docking run in Research and open its result summary.
  2. Confirm each result’s ligand, receptor, seed and attempt.
  3. Read the pose’s score name, value, ranking direction and available QC.
  4. Page through results. Open a candidate record for a pose you want to compare; see chapter 16.

Check: The summary shows a read time, with results paged by task and up to five poses per task. Missing scores or QC remain missing; do not treat them as zero or passed.

Troubleshooting: If no results are available, check whether the run is queued or active and then consult logs. Retry a failed read. Scores cannot be averaged across engines and do not establish binding or activity.

15.2 Inspect MD progress, checkpoints and analyses

  1. Filter Research to MD and open the run.
  2. In its summary, check elapsed simulation time against the target, performance, step count and checkpoint state.
  3. Check whether this attempt resumed from a checkpoint and identify the source attempt.
  4. Review existing analyses in the summary. Use the desktop app to configure or run further analyses.

Check: Unavailable data stays missing. Finding a checkpoint does not mean the phone resumed the job.

Troubleshooting: If there is no analysis, check for readable outputs on the computer. If a run can resume, verify and continue on the desktop. Reaching a target time or finishing execution is not proof of convergence or mechanism.

15.3 Select the right log

  1. Open Errors and Logs from the run or its card.
  2. Choose Worker for execution output or Scheduler for job scheduling output.
  3. From a Docking result, open its task log to inspect that specific result.
  4. Move to earlier log pages or return to the latest available output.

Check: The log shows the read time, byte range and total size. Confirm source and attempt before interpreting an error.

Troubleshooting: A log not yet present may appear later; retry the latest page. For a log opened from a historical message, check the attempt if it differs from the current one.

15.4 Search, follow and copy logs

  1. Search the current page and use previous and next match controls.
  2. Filter to error keywords, then turn the filter off when you need full context.
  3. With a live connection and an automatic interval, turn on follow-latest. Searching, scrolling up or reading an older page pauses following; turn it back on when finished.
  4. Use Copy Current Page to copy that page.

Check: The count and follow indicator show the current state. Search and filtering cover only the current page, up to 16 KiB. Line numbers are page-relative. Copying the page does not download the full log.

Troubleshooting: Search older pages when needed. Following is unavailable offline or in manual mode; manually open the latest page. If copy fails, long-press to select text. Interpret keyword matches with exit codes and context.

16. Record notes, save favourites and compare candidates

16.1 Save a note and favourite a run

  1. Open run details and choose Run Notes.
  2. Favourite runs you revisit often.
  3. Set the research review status and write observations, questions or next steps.
  4. Save. Return to Research Records and open Run Notes to find or edit it.

Check: Favourites, review status, notes and edit times appear in the list. Marking a note reviewed does not mark the calculation finished. The record is saved locally first.

Troubleshooting: On save failure, remain in the editor and check storage. If a record is missing, confirm the account and device. If prompted to discard unsaved edits, go back and save to keep them.

16.2 Save a pose to the candidate list

  1. Open a candidate record for a pose from the Docking summary.
  2. Review its provenance and score, set a review status and add notes.
  3. Save and find the entry in the candidate list under Research Records.
  4. Open the source run or expand full provenance for additional fields.

Check: The candidate retains pose provenance, scores and read time. Edit the original record to update its note.

Troubleshooting: A pose without a stable identifier cannot be saved; check the desktop result. If the source is unavailable, saved provenance remains readable until you reconnect. Deleting a research record does not delete the computation output. Read the confirmation first when sync is involved.

16.3 Compare two to four records

  1. Choose Run Notes or the candidate list in Research Records.
  2. Mark two to four entries for comparison or export.
  3. Open the comparison of selected entries.
  4. Scroll horizontally to review sources, engines, metrics, parameters, read times and notes. Highlighted fields differ.

Check: Missing values are shown as a dash. A matching context is a hint, not a substitute for checking scientific conditions.

Troubleshooting: Adjust your selection if there are fewer than two or more than four. You can read records from different receptors, runs or scoring contexts side by side, but do not rank or merge incompatible scores. Refresh and update stale records from their source.

16.4 Export a summary and confirm delivery

  1. Export selected records or the current list in Research Records, or export a summary from a comparison.
  2. Choose Markdown (.md) or JSON (.json) and inspect the preview.
  3. Save or share on Android or iOS, or download from the browser, then choose a destination in the system dialog.
  4. Copy text if a file is unnecessary. Check notes and provenance before sharing; remove anything you do not intend to disclose.

Check: Open the saved file or confirm reception in the destination app. A summary has saved records, notes and provenance, not the full molecular library, trajectories or calculation files.

Troubleshooting: Cancelling save or share does not delete the source record. Retry or copy the text if export fails. Opening a share sheet does not prove delivery.

17. Keep pages for offline use

17.1 Save a run summary and selected pages

  1. Open run details while connected and wait for a successful read.
  2. Save the run summary. To retain a result or log page, open it and retain the current loaded page.
  3. Load and retain each additional page separately.
  4. Review saved result and log pages, their ranges, read times and save times.

Check: The page reports successful retention. A summary does not download the entire run. New online reads can replace a saved copy, so this is not an immutable backup.

Troubleshooting: If retention is disabled, wait for the page to finish loading. If storage is full, unpin material you no longer need as described in 17.3. A visible page is not a saved copy unless the app confirms it.

17.2 Reopen offline and identify missing pages

  1. Reopen the app with the original account and connection. Look for the offline-copy label and original read time.
  2. In Settings under Offline Records, open material from an explicitly retained run.
  3. Expand saved result and log pages and select the page you need.
  4. After reconnecting, refresh tasks and reread any pages that need updating.

Check: Offline copies show their original read time. Normal reading caches recent content; explicit retention keeps the summaries and pages you selected.

Troubleshooting: Choose an existing saved page if another was not saved, or reconnect and fetch it. If an offline run is missing, check the account and device. Signing out or unpairing can clear local copies; reconnecting is not a substitute for export.

17.3 Manage storage and release retained pages

  1. Open Settings → Offline Records to see usage by connection, app and retained content.
  2. Stop retaining a whole run or an individual page from its saved-page list.
  3. To release all retained pages for a run, use its detail action, confirm and recheck usage.
  4. Clear the current connection’s offline records only after confirming you do not need them.

Check: The app-wide limits are 40 runs, 12 result or log pages per run and 20 MiB total. Retained copies count toward these limits but are not automatically evicted. Releasing retention makes copies eligible for ordinary cache eviction. Clearing a local copy does not delete server outputs.

Troubleshooting: Releasing a retained copy need not immediately reduce usage because it may remain in the cache. Check device storage if saving or clearing fails. Do not sign out as a substitute for managing storage.

18. Edit and submit a pending plan

18.1 Open a desktop project or saved plan

  1. Save the desktop project; the phone cannot read unsaved desktop edits.
  2. Under Settings → Mobile Project and Task Authorization, select the paired monitoring agent’s Device.json and grant a duration. Editing plans is the default. To allow actual submission, enable the separate mobile submission permission on the desktop. A permission grant alone does not start a job; phone confirmation is still required.
  3. On the phone, choose the correct device and refresh permissions. Open plans under Research or from the signed-in account view.
  4. Open a desktop project to configure a new plan, or view a saved plan.
  5. Check the project, compute host, engine and number of tasks before editing.

Check: A desktop project produces an independent pending plan without altering the source. Only a pending plan that has not begun executing can be edited where supported.

Troubleshooting: Save the project on the computer and refresh plans if it is missing. For permission errors, verify the paired agent, duration and submission approval on the desktop and refresh the phone. Check unsupported project configuration on the desktop; do not treat an active run as editable.

18.2 Edit parameters and recover local drafts

  1. Docking plans can expose CPU threads per ligand, parallel ligands, exhaustiveness, maximum poses, scoring function and seed. Set the energy range (kcal/mol) only when the form shows it. For a single box, use center and size XYZ in Å.
  2. GNINA execution can be CPU-only or allow GPU where supported. The displayed CNN scoring mode describes the configuration; it is not editable here. Edit receptor-specific boxes on the desktop.
  3. MD resource settings can include threads per rank, MPI ranks, GPUs, memory (GiB), queue time, partition, account, QoS, maximum runtime (hours) and execution mode. These do not change the scientific settings in an existing TPR.
  4. Confirm that edits were saved locally but not sent. Reopen the local draft if needed, inspect its values and refresh the source online before previewing.

Check: Follow the displayed units and ranges. A local draft is only phone input: it is not a desktop plan and has started no calculation. Use comma-separated seeds and the form’s queue time format.

Troubleshooting: Correct highlighted values. If the desktop source changed, inspect the old draft before discarding it and re-entering changes against the latest source. Do not overwrite a changed project with an old draft. If local saving fails, keep the page open and check storage.

18.3 Preview changes and save a pending plan

  1. Finish editing and preview the changes.
  2. Compare before and after. For a new desktop-derived plan, also review its resource summary.
  3. Confirm and save as pending.
  4. Read the save result, inspect a verified desktop receipt if shown and check the saved-plan list.

Check: The app reports a pending plan with no submitted computation, or confirms an independent plan and an unchanged source project. Saving does not launch a job.

Troubleshooting: An existing plan needs a change before preview; a new plan can use the original settings. Refresh and preview again if the source or preview changes. If the save outcome is unknown, query or retry the same save rather than creating a replacement plan.

18.4 Check resources, submit and recover an unknown outcome

  1. Grant time-limited submission permission on the desktop and refresh the phone. Save local edits to the desktop or explicitly discard an unneeded draft first.
  2. Open the saved pending plan and review submission.
  3. Confirm host, engine, task count and CPU concurrency, or MD threads, ranks, GPUs, memory and queue runtime.
  4. Check the confirmation and start computation only when ready. This sends a real job to the compute host.
  5. Refresh plan state. Once an associated run appears, open progress, results, worker logs or scheduler logs.

Check: Submission is recorded before the current state is shown. Submission and queueing are not completion; check the associated run.

Troubleshooting: Check acknowledgement, permission and unsaved edits if Start is disabled. After an interruption, recover the same submission or refresh the plan rather than starting another one. Reopen the original account, service and host to process a retained receipt. If receipt storage fails, restore local storage and retain the original operation; do not clear data to bypass recovery.
